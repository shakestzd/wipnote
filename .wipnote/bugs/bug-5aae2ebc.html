Description

execTee wraps the caller's stdout and stderr in two separate io.MultiWriters that both also write the run log. exec copies the command's stdout and stderr in two goroutines, so when the caller passes one writer for both (the test does: SetOut and SetErr share a bytes.Buffer) the writes race. go test -race reports the race in bytes.Buffer.Write. A racing write can come back short; MultiWriter then stops with ErrShortWrite before writing the log, so the line never reaches the run log and FirstError is recorded empty. CI saw this on PR #346 (run_test.go:92: first error = ""). Separately, any passthrough write error, such as a closed terminal, also drops the line from the log. Why A flaky required CI check blocks merges and hides real failures, and the run log is the record wipnote keeps, so it must not lose lines when the terminal writer misbehaves Acceptance Criteria execTee serialises both streams through one lock, writes the log before the passthrough, and keeps logging when the passthrough fails; go test -race on the run wrapper tests is clean and a regression test shows a failing passthrough still logs every line
