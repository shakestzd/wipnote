DesignPending

Problem

Questions an orchestrator owes the owner live only in the agent's prose. In the 2026-11-07 session (issue #336) they got buried under later replies, were answered turns after the work they affected, and the owner had to ask for the question tool at least five times. Work either waited on an answer or went ahead on a default that the item never recorded.

Goals

  1. Every open owner question is a record on a feature, bug or spike, listed in one place.
  2. Work continues on the recommended option unless a question is marked blocking, and the item records the assumption.
  3. A late answer that differs from the assumption is flagged and reopens the affected item or slice.
  4. Open questions are asked through the harness question tool in batches of at most four, recommended option first.
  5. The owner sees open questions in a side pane and a band count, and can answer from there.

Constraints

  • The store stays HTML-canonical; the question record is a node property, like the research record.
  • No new runtime dependencies.
  • Files under 500 lines, functions under 50.
  • Hooks stay thin wrappers over `wipnote hook <handler>` and must not slow the hot path noticeably.

#1 Question record and `wipnote question add|list|answer` Store owner questions as a node property on features, bugs and spikes, modelled on the research record. M Low Complex Promoted Approved 1 Q
What

Store owner questions as a node property on features, bugs and spikes, modelled on the research record. Add wipnote question add, list and answer, with 2-4 options, an optional recommended option, an optional blocking flag, a status, and an answer stored on the item.

Why

Gives every open question a home that survives across turns and shows in lineage (goal 1). All later slices read or write this record.

Files
core/question/record.go (new), core/question/record_test.go (new), cmd/wipnote/question_cmd.go (new), cmd/wipnote/question_list.go (new), cmd/wipnote/question_cmd_test.go (new), cmd/wipnote/main.go
Done when
  • `question add <item> "<text>" --option k:label[:tradeoff] ... [--recommended k] [--blocking]` stores an open record and prints its id.
  • `add` refuses fewer than 2 or more than 4 options, an unknown recommended key, and items that are not a feature, bug or spike.
  • `question list [--item <id>] [--open] [--format json]` spans all item types; `--open` means status open or assumed; rows carry status.
  • `question answer <qid> <key> [--note]` records answer and time; an unknown key is refused, a re-answer needs `--force`.
Decisions

Trigger: an orchestrator or worker runs wipnote question add on a work item. State: a list of Question records in one node property, read and merged the way research.FromNode / research.Merge (core/research/record.go) handle the research record (cmd/wipnote/research_cmd.go saveResearchRecord, openItem). The field set extends planyaml.PlanQuestion (id, text, recommended, options, answer) with blocking, status, raised_by, raised_at, source_id, assumed, note and answered_at; the option tradeoff is a new field beside QuestionOption's key and label. Status: open on add; assumed, confirmed and overturned are set by slice 2. --force re-answer exists so an overturned question can be corrected; slice 2 re-runs its overturn check on it. Payload: list --format json rows carry item id, item title, question id, text, options, recommended, blocking, status, assumed, raised_by, age and answer, so the mod and the hook read one shape. Items that no longer resolve are skipped. Size: list and its JSON rendering live in question_list.go so question_cmd.go stays under 500 lines once slice 2 adds assume. Rejected: steps (a done-flag checklist, no options or answer); edges (relations, not payload); a separate questions/ directory of files (a second store to sync, and the answer would not sit on the item).

#2 Non-blocking by default, blocking questions in execute-preview When work goes ahead with an open non-blocking question, record the recommended option as assumed. M Med Standard Promoted Approved
What

When work goes ahead with an open non-blocking question, record the recommended option as assumed. A later answer that differs marks the assumption overturned and reopens the item; add bug reopen and spike reopen beside the existing feature reopen. Blocking questions warn at start and are listed in execute-preview.

Why

Work keeps moving without hiding the default it chose (goal 2), and a changed answer is visible and acted on (goal 3).

Files
core/question/record.go, cmd/wipnote/question_cmd.go, cmd/wipnote/workitem_set_status.go, cmd/wipnote/feature_reopen.go, cmd/wipnote/workitem_reopen.go (new), cmd/wipnote/execute_preview.go, plugin/skills/execute/SKILL.md
Done when
  • `question assume <qid>` and `<type> start` record assumed = recommended for open non-blocking questions; start never fails on question errors.
  • Start warns on an open blocking question and records no assumption; complete warns when open questions remain.
  • An answer equal to assumed confirms; a different one overturns and reopens a done feature, bug or spike, or names the in-progress item.
  • `execute-preview` lists open blocking questions per item; the execute skill says not to dispatch an item with one.
Decisions

Trigger: item start (wiStartCmd in cmd/wipnote/workitem.go calls runWiSetStatus; the hook goes in afterStart in workitem_set_status.go) or an explicit question assume; later, question answer. State: status open -> assumed on start, assumed -> confirmed or overturned on answer. Questions without a recommended option stay open on start. Reopen: only feature reopen exists today (feature_reopen.go); workitem_reopen.go adds the bug and spike verbs on the same code path. Payload: execute-preview gains a questions list of blocking records per item. Rejected: blocking every open question (defeats the non-blocking default the owner chose); silently keeping the assumption on a different answer (the owner chose flag-and-reopen); a follow-up item for rework (owner chose reopen).

What

When wipnote delegate result runs, file each structured worker question from the run (outbox delegate reply --ask files and hook-captured AskUserQuestion calls, answered or not, open or closed run) as a question record on the worker's work item, once. Add --recommended to delegate reply --ask. Update the worker brief to raise owner questions that way.

Why

Worker questions are the largest source in the issue's session; they must land on the item instead of in report prose (goal 1).

Files
internal/delegate/session/questions.go, internal/delegate/session/mail.go, cmd/wipnote/delegate_mail.go, cmd/wipnote/delegate_reply.go, plugin/skills/delegate/SKILL.md
Done when
  • `delegate result NAME` on a closed run files each unfiled worker ask on the worker's item and prints the ids; a re-run files nothing.
  • A question already answered through `delegate answer` is filed with its answer; permission prompts are not filed.
  • A worker with no work item gets a warning naming the questions instead of a silent drop.
  • The delegate skill tells workers to use `delegate reply --ask` (with `--recommended`) and not to list questions in the report.
Decisions

Trigger: wipnote delegate result NAME (session.Result in internal/delegate/session/mail.go). Source: session.Questions returns only pending asks and nothing for a closed run (questions.go runQuestions), so this slice adds a reader over all of the run's ask events and question files, excluding KindPermission. The item comes from the ledger row's WorkItem (core/delegationledger/record.go). State: each filed record sets source_id to the worker question id (tool use id or <task-id>-q); a re-run skips ids already present. Payload: worker options are bare strings; each becomes an option with key = its index and no trade-off text. recommended comes from the new delegate reply --ask --recommended, otherwise empty. Note: AskUserQuestion is not available in Claude subagents (agent-sdk user-input docs); hook-captured asks only come from workers that run as full sessions, so the outbox file is the primary path. Rejected: parsing an "Owner questions" section from the report prose (owner chose structured only; depends on a heading format workers drift from).

#4 Ask with the question tool in batches; Stop hook nudge Add an orchestrator rule to ask open questions with the harness question tool, at most four per call, recommended option first. M Med Standard Promoted Approved
What

Add an orchestrator rule to ask open questions with the harness question tool, at most four per call, recommended option first. Add a Stop hook check that blocks once when a reply ends with a prose question while open records exist, on Claude Code and Codex; Antigravity gets the prompt rule only.

Why

The owner asked for the question tool five times in one session; the rule and the nudge make it the default (goal 4).

Files
cmd/wipnote/prompts/system-prompt.md, core/hooks/missing_events.go, core/hooks/runner.go, core/hooks/missing_events_test.go, cmd/wipnote/hook.go
Done when
  • The orchestrator prompt says to ask open questions with the question tool, at most four per call, recommended first, and to record answers with `question answer`.
  • Stop blocks with a reason naming open question ids when the last non-empty line outside a code block ends with "?" and open records exist.
  • Stop allows when stop_hook_active is true, in delegate worker sessions, and on Antigravity.
  • A benchmark shows the check adds under 5 ms when no question records exist.
Decisions

Trigger: the Stop hook (hooks.Stop in core/hooks/missing_events.go, dispatched from cmd/wipnote/hook.go; manifest entry already targets claude, codex and antigravity). State: reads open records via the slice 1 list. Loop guard is stop_hook_active, verified in both Claude Code and Codex docs; runner.go already parses last_assistant_message and gains StopHookActive. Workers: delegated workers also fire Stop; the check skips sessions the delegate launcher marks as workers (WIPNOTE_DELEGATE_RUN is set; confirm it reaches the hook process during the slice), so only the orchestrator is nudged. Payload: decision "block" with a reason naming the question ids and the tool to use. Codex uses the existing emitter (codexEventAcceptsDecision covers Stop in core/hooks/harness_response.go). Antigravity's Stop format is undocumented, so it gets the prompt rule alone. Rejected: a context note only (prose questions still reach the owner first); no hook (owner chose block once).

What

Add a wipnote-questions mod pane that lists open questions across items and answers them with wipnote question answer, showing the command's result. Show an open and blocking count in the orchestra band, a toast on a new blocking question, and open questions on ref cards.

Why

The owner sees every open decision in one place and can answer without searching the chat (goal 5).

Files
mods/wipnote-questions/.claude-plugin/plugin.json (new), mods/wipnote-questions/hooks/hooks.json (new), mods/wipnote-questions/hooks/register.tsx (new), mods/wipnote-questions/hooks/model.ts (new), mods/wipnote-questions/types/index.d.ts (new), mods/wipnote-questions/tsconfig.json (new), mods/wipnote-questions/tests/model.test.ts (new), mods/wipnote-questions/README.md (new), mods/wipnote-orchestra/hooks/register.tsx, mods/wipnote-orchestra/hooks/band.tsx, mods/wipnote-orchestra/hooks/refcards.tsx, cmd/wipnote/mods_test.go
Done when
  • The pane lists open questions from `question list --open --format json` with item, age, blocking and recommended, polling while placed.
  • Choosing an option runs `question answer`, toasts its output (including "overturned, <item> reopened"), and the row leaves the list.
  • The band shows "N open questions · M blocking" when N > 0; a new blocking question toasts; ref cards show the item's open questions.
  • A new mods_test test checks the wipnote-questions mod has its manifest and hooks files.
Decisions

Trigger: pane open (poll while placed), band refresh, card render. State: none in the mod; all data from wipnote question list --format json. Orchestra: polling lives in mods/wipnote-orchestra/hooks/register.tsx, so the count and toast detection go there; band.tsx only draws. Ref cards call question list --item <id> --open --format json beside the existing show call in refcards.tsx. Loading: the launcher finds mods by reading the mods/ folder and mirrors the tree on deploy; no registration is needed. Payload: the slice 1 JSON row shape. Rejected: a file watch on the store (the existing mods poll the CLI and the store may be outside the repo); putting the list in the band itself (too little room).
