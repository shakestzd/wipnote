## Problem wipnote has two delegation paths. The `mods/codex-herdr-pane` mod (TypeScript, Claude Code mods engine) wraps one-shot `codex exec`, `codex review`, `ccx task` and `claude -p` calls in a herdr pane and writes a run folder (feat-a1df60c2). orch (Python, on the owner's machine only) drives interactive Claude and Codex sessions in herdr panes through a file mailbox. wipnote only reads orch's files (`internal/orchlink`, feat-ac66c687). `docs/design/orch-integration.md` line 16 splits the work: "the mod covers one-shot runs, orch covers interactive sessions". The owner replaced that split. Delegation becomes a native wipnote feature written in Go in the wipnote binary, with orch as the reference and the mod absorbed. The result is ONE path. Today a delegation leaves only hook events. No canonical record links it to a work item (feat-dd8b0cde). orch facts live outside the project and never reach `.wipnote/`. ## Non-goals - herdr-orch-style task DAGs, auto-dispatch, resource leases, PR CI watch, schedules and web UI. These are prior art, not scope. - Remote machines over SSH, and phone or chat front ends. - Parking an idle worker between tasks. Stop-when-done is the rule; slice 20 resumes a stopped worker instead (decision E). - Auto-accepting a worker's trust or permission prompts (brgr does this; we do not copy it by default). - Replacing Claude Code's native subagents (Task/Agent) or Codex's native subagents. - A dashboard or web view. The dashboard is gone; lineage and the CLI are the read surfaces. - Antigravity workers in v1 (q-antigravity answered no). The delegate skill is not shipped in the Antigravity tree. ## Design decisions (rationale in each slice's decisions_notes) 1. **No daemon.** Every verb is a short CLI process, a bounded wait, or a process that lives in a herdr pane. Hooks write one small file and return. A missing or slow writer daemon never delays a hook or the launcher (user rule: daemons never block Claude). 2. **Workers run under wipnote's launchers and claim the work item.** `spawn` starts `wipnote claude` or `wipnote codex` in the pane with `WIPNOTE_DELEGATE_RUN=<run-id>`. wipnote's own plugin hooks fire, so no `--settings` hook file is needed. The worker claims the item through the normal start path (owner, 2026-10-25; see Claims below). The launcher passes no `--settings` today (code search, 2026-10-25). The `--settings` risk remains only for orch during migration (Phase B check B1). 3. **One writer per file.** Each mailbox message is its own file, written by temp file plus rename. Each process appends to its own events file. This avoids the APFS O_APPEND hazard (arch card daemon-purpose-outlives-sqlite) and any flock across a host-container bind mount. 4. **One canonical record type (Q4) holding spawn and stop (Q3).** `.wipnote/delegations-ledger.html` has one row per run with `mode=oneshot|interactive`. Spawn opens the row. Exit or stop closes it. Usage and session ids enrich it. Tool and prompt events are not copied: they duplicate `agent_events`. 5. **Settle on durable signals.** A wait ends on the worker's result file for the current task (decision R), an exit file, or the Stop hook's "turn ended" signal (reported as idle_no_result). herdr agent state is only a hint: herdr's docs say `agent wait` observes state, not job completion. cbds and herdr-orch settle the same way. 6. **Keep the run-folder contract.** The files are raw.log, clean.log, clean.md, last.md, usage, exit, start, end, label, host and run.html, as in feat-a1df60c2. The report the caller sees keeps the mod's format, so prompts and viewers keep working. 7. **Layout.** The engine lives in `internal/delegate/` (cmd imports internal). The ledger lives in `core/delegationledger/`, beside `core/sessionledger` and `core/gateledger`. herdr is driven through its CLI behind an interface, not the socket API: herdr-orch pins socket protocol 22, which changes between releases. ## Owner decisions 2026-10-25 (round 3) - **R. No claim store or outcome is added. Facts from the code (2026-10-25): - An episode is one row per (session, agent, work item), sharded by root session in `.wipnote/claims/`. Outcomes are `completed`, `released`, `abandoned` and `expired`. There is no `suspended`. - `wipnote <kind> start` opens an episode (idempotent per session). `checkLiveCollisionGate` refuses it while another live root session holds the item, unless `--force`. The caller's own family (same session, or same root) is not a collision. - A worker's episode is rooted at its own session, because `rootSessionFor(nil, ...)` falls back to the session id. So today the gate would refuse a worker while the orchestrator holds the item. - Completion by any session closes every open episode on the item (`CloseWorkItem`, written for the orchestrator hand-off case). - SessionEnd closes only that session's rows as `abandoned`. The stale-session reaper and `wipnote claims reconcile` close a dead session's rows as `expired`. Defined behaviour, which follows from that model whatever q-claim-handoff decides: - **How the worker claims.** Its brief begins with `wipnote <kind> start <id>`, so the item lock, the collision gate and the ledger write run unchanged. `spawn` returns before the worker claims, so `delegate wait` and `list` check that the episode appeared and report it if not. `spawn` needs a work item: `--work-item`, or else the caller's active claim. It refuses when neither exists. - **The worker stays a root session.** `spawn` does not set `WIPNOTE_PARENT_SESSION`, which would mark the worker as a subagent and drop its sessions-ledger row. The caller link travels in `WIPNOTE_DELEGATE_CALLER` and in the delegations ledger. - **Worker stop.** `delegate stop` asks the worker to exit. The worker's own SessionEnd closes its episode as `abandoned`. The delegations ledger records `end_reason=stop`, so lineage shows the stop was deliberate. The caller never writes the worker's shard while the worker lives. - **Worker crash or lost pane.** No SessionEnd fires. A `delegate` command in the caller (`wait`, `list` or `stop`) sees the pane gone and confirms that no worker process remains. It then closes only that worker session's episodes as `expired`, the same session-scoped close that `closeClaimEpisodesForSession` uses. `wipnote claims reconcile` stays the backstop. This depends on bug-01f182e5 (reconcile treats live sessions as dead) being fixed first, or reconcile would expire live workers. - **wait timeout.** It changes no claim. The worker keeps running and keeps its episode. - **Orchestrator ends first.** Its SessionEnd closes only its own rows. Workers keep their claims, and their delegation rows stay open until they end. - **Completion.** Whoever completes the item closes every open episode on it, worker and orchestrator alike (existing `CloseWorkItem`). **Handoff (q-claim-handoff answered 2026-10-25: co-claim, workers count as family).** The orchestrator keeps its episode while a worker holds its own, so the claim never leaves the orchestrator and nothing has to return. The claim gate (`liveForeignClaims` and `checkLiveCollisionGate` in `cmd/wipnote/claim_ledger.go`, called by `<kind> start` in `cmd/wipnote/workitem.go`) treats an episode as family in two cases: - It is held by a worker session listed in `worker_sessions` of an open interactive delegation row whose `caller_session` is the caller. This lets the orchestrator re-start or review. - The caller is a worker (`WIPNOTE_DELEGATE_RUN` names an open row) and the episode is held by that row's `caller_session` or its root. This lets the worker claim beside the orchestrator. An unreadable delegations ledger fails open, as an unreadable claim ledger does today. Completion has no claim gate, so the orchestrator can review and complete. Completion closes every open episode on the item, the worker's included (`CloseWorkItem`). The guidance therefore says to stop the worker before completing. **Concurrency (q-concurrent-workers answered 2026-10-25: one worker per item in v1).** `spawn` refuses when an open interactive row for the item has a live worker. A row whose pane is gone is closed first, through the worker-loss path. Add --container to delegate run and spawn. Payload: the boot line runs devcontainer up --workspace-folder <root> (idempotent), then devcontainer exec --workspace-folder wipnote claude|codex. up prints JSON with remoteWorkspaceFolder, which maps run-folder paths into the container. Reuse: scripts/devcontainer.sh already uses devcontainer up and exec with --workspace-folder and finds the container by the label devcontainer.local_folder.
